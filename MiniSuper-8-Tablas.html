1. Veredicto rápido

El documento está bien escrito como especificación funcional, pero no está alineado con tu objetivo: describe un sistema de unas 14–15 tablas (el punto 3 de implementación pide 10 entidades, más detalle de compras, movimientos de caja, configuración, roles y métodos de pago implícitos) y no menciona PostgreSQL ni pgAdmin en ningún lado. Hay que recortar alcance y agregar la parte técnica de la base de datos.

  • Productos, categorías, proveedores

  • Convención de nombres

5. Relaciones

RelaciónTipoSignificado
categorias → productos1 : NUna categoría agrupa muchos productos.
usuarios → ventas1 : NUn cajero realiza muchas ventas (y un admin puede cancelarlas).
ventas → detalle_ventas1 : NUna venta tiene una o más partidas.
productos → detalle_ventas1 : NUn producto aparece en muchas ventas.
proveedores → compras1 : NUn proveedor surte muchas compras.

compras → detalle_compras1 : NUna compra tiene una o más partidas.
productos → detalle_compras1 : NUn producto se compra muchas veces.

ventas ↔ productos y compras ↔ productos son relaciones N : M resueltas por las tablas de detalle.

6. Reglas de base de datos

  • Venta atómica: en una sola transacción (BEGIN … COMMIT): insertar en ventas, insertar partidas en detalle_ventas y restar productos.existencia. Si cualquier paso falla, ROLLBACK.
  • Sin sobreventa: descontar con UPDATE productos SET existencia = existencia - $cant WHERE id = $id AND existencia >= $cant; si no afecta una fila, cancelar la transacción. El CHECK (existencia >= 0) es la segunda barrera.
  • Compra atómica: igual que la venta, pero sumando existencia (y opcionalmente actualizando productos.costo).
  • Cancelación: nunca borrar. Cambiar estado a 'cancelada', llenar quién/cuándo/motivo y regresar existencias, todo en una transacción, y solo si el estado actual es 'completada' (así se repone una sola vez).
  • Nada se elimina si tiene historial: ON DELETE RESTRICT en todas las llaves foráneas y uso de activo = FALSE.
  • Precios congelados: las partidas guardan precio y tasa del momento; cambiar el precio de un producto no altera ventas pasadas.
  • Permisos: validar el rol en el backend en cada operación; el cajero no crea usuarios, no edita productos, no registra compras ni cancela ventas.
  • Índices: además de los UNIQUE, crear índices en productos(nombre), ventas(fecha) y en cada llave foránea.

7. Pasos de trabajo

  1. Decidir el backend (lenguaje y si es web o escritorio).
  2. Escribir 01_esquema.sql con las 8 tablas en este orden (por dependencias): usuarios, categorias, proveedores, productos, ventas, detalle_ventas, compras, detalle_compras.
  3. Escribir 02_datos_iniciales.sql: un administrador, un cajero, 4–5 categorías, 2 proveedores y ~20 productos de prueba.
  4. Instalar PostgreSQL + pgAdmin, crear la base minisuper y ejecutar ambos scripts.
  5. Revisar el diagrama en pgAdmin (clic derecho en la base → ERD For Database).
  6. Programar el flujo mínimo: login → catálogo de productos → venta con descuento de inventario.
  7. Agregar compras, cancelaciones y reportes (ventas por fecha, más vendidos, por método de pago, existencia baja).
  8. Probar casos límite: código duplicado, cantidad negativa, producto inactivo, pago insuficiente, stock insuficiente, cancelar dos veces.
  9. Documentar instalación, ejecución y respaldo/restauración con pg_dump.

9. Fase 2 (después de las 8 tablas)

Estas tablas se dejaron fuera para respetar el límite de 8. El diseño actual permite agregarlas sin rehacer nada:
  • movimientos_inventario: historial completo y ajustes manuales con motivo.
  • sesiones_caja + movimientos_caja: apertura, cierre, retiros y diferencias.
  • configuracion: datos de la tienda, política de sobreventa, umbral de stock.
  • pagos: solo si se necesitan pagos mixtos (parte efectivo, parte tarjeta).
